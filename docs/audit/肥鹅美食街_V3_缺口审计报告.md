# 《肥鹅美食街》V3 开发档案缺口审计报告

> 审计对象：`肥鹅美食街_V3_完整开发档案`  
> 审计标准：是否能不再依赖口头补充，直接交给关卡策划、UI、美术、Cocos/后端与 QA 分工生产。  
> 结论：**V3 不是“完整生产包”，更准确应称为“系统架构 + 110日节奏蓝图 + UI/美术规范框架”。**

# 二、P0：不补就不能称“完整开发档案”的缺口

## 1. 关卡不是“完整110日关卡”，目前只是完整110日节奏表

当前 Day11~110 没有逐日完整给出：

- 每一单 `OrderId`
- 顾客
- 需求物品及数量
- 需求物品具体等级
- 订单出现顺序
- 并行槽位变化
- 金币奖励
- 额外奖励
- 所属 Producer
- 所需 Recipe
- 所需 Cookware
- 理论 P50/P90
- 实际烹饪时间
- Producer 冷却影响
- 建设节点
- 当日建设金币
- 当日剧情
- 解锁项
- 活动 Hook

因此现在的 Day21 示例实际上只是：

```text
Day21
阶段=P3
订单数=5
P50=240
主链=肉类/谷物/早餐/调味
```

这不是一张真正能导入游戏的关卡配置。

### 完成标准

最终每个 Day 必须能直接生成：

```json
{
  "day": 21,
  "orders": [
    {
      "id": "D021_O01",
      "customerId": "...",
      "requirements": [
        {"itemId":"...", "count":1}
      ],
      "reward": {"coin":0},
      "dependencies": {
        "producerIds":[],
        "recipeIds":[],
        "cookwareIds":[]
      }
    }
  ],
  "buildNodes": [],
  "storyBeats": [],
  "unlocks": [],
  "eventHooks": []
}
```

110 天全部如此才算“关卡完整”。

## 2. 缺完整 Item / 合成链数据库

目前只有少量公开案例，例如肉类链、菌香芝士卷。

真正生产需要：

```text
所有 Item
→ 所属 Chain
→ Level
→ MergeTo
→ 可否加工
→ 加工后产物
→ 来源 Producer
→ 解锁 Day
→ 出售价格
→ 图鉴信息
→ 美术 AssetId
```

如果没有这张总表，程序、关卡和美术三方无法对齐。

### 必须新增

- `items_master.csv`
- `merge_chains.csv`
- `transformations.csv`
- `item_unlocks.csv`

---

- 等级
- 升级链
- 每级产出池

- 高阶直出概率

- Capacity
- Cooldown

- Boost 行为
- 活动 Override

`producer_master.csv`

```text

capacity
cooldown_sec
```

```text

orders = array
days = array
```

并没有真正校验各字段。

最终 Schema 必须对：
- ID 格式
- Enum
- 引用
- 数值范围
- Required
- Unique
- 时间
- Reward

# 六、最终审计结论

如果目标只是：

> “研究《肥鹅美食街》，理解它为什么成立，并做一个同类游戏的架构。”

V3 已经够用。

如果目标是：

> “资料交给 Codex、美术和策划，不再找我确认，就开始把一个完整商业版本做出来。”

**V3 还不够。**

最大的问题不是“还缺几段文字”，而是缺了 5 个真正的数据主体：

```text
① 完整110日逐单关卡数据库
② 全 Item / Producer / Recipe / Cookware 数据库
③ 46页逐页 UI Wireframe + 状态设计
④ 全量 Asset Manifest + 角色/建筑 Canon
⑤ 完整经济 / 建设 / 活动 / 剧情内容数据库
```

这五项补齐以后，才建议把版本称为：

**V4 Production Bible / 生产总档案。**
