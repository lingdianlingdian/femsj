# 3. 核心循环已经可以精确描述

```text
经营日开始
  ↓
多个并行顾客订单
  ↓
选择生产器
  ↓
消耗体力 → 生成基础/中阶材料
  ↓
┌──────────────────────┐
│ 路径A：继续二合升阶   │
│ 路径B：把当前材料送厨具│
└──────────────────────┘
  ↓
厨具等待 / 生产器冷却 / 棋盘空间管理
  ↓
获得订单所需食材或成品菜
  ↓
交付订单
  ↓
金币/资源/活动进度
  ↓
完成当日目标
  ↓
金币修复/扩建美食街
  ↓
剧情/角色/区域/新内容
  ↓
下一经营日
```

最关键的设计不是“二合”，而是中间这个分叉：

> 同一份材料，到底继续向上合成，还是现在投入厨具变成另一种菜？

这让传统 Merge-2 的“无脑向上合”变成资源调度。

# 4. 新手与棋盘

高可信实机拆解确认：

```text
剧情开场
→ 4×7 教学盘
   - 发射
   - 合成
   - 解锁地块
   - 交付订单
→ 9×7 正式主棋盘
```

正式盘共 63 格。

未解锁区域不是无意义散格，而是成块封锁，并把：

- 何时解锁；
- 解锁奖励；

直接显示给玩家。

这等于把棋盘空间本身做成一个“可见进度条”。

来源：[S02]

### 对我们开发的意义

Board 不应只有：

```ts
Cell { itemId }
```

而应该至少：

```ts
Cell {
  state: OPEN | LOCKED | BLOCKED
  unlockGroupId?: string
  unlockCondition?: Condition
}
```

锁区必须是 Group，而不是单格逻辑。

# 5. 物品系统必须做成“转换图”，不能只做一条 merge_to

## 5.1 已确认肉类链

公开实机拆解给出了完整实例：

```text
肉肠 + 肉肠
→ 培根

培根 + 培根
→ 肉丸

肉丸 + 肉丸
→ 牛胸肉
```

但同一个链又可以分叉：

```text
肉肠 + 烤架
→ 烤肠

牛胸肉 + 烤架
→ 烟熏牛胸肉
```

来源：[S03]

如果把肉肠视作该截取链的基础节点：

```text
1 牛胸肉 = 8 肉肠
```

这只是理论二合数量，不包含生产器随机性、体力、冷却和等待。

## 5.2 多输入菜谱

另一个明确实例：

```text
蘑菇
+ 洋葱
+ 芝士片
+ 备菜台
→ 菌香芝士卷
```

来源：[S03]

因此正确数据结构应是：

```text
Item
  ↕
TransformationGraph

Transformation
├─ MERGE2
├─ COOK
├─ OPEN
├─ EXCHANGE
└─ EVENT
```

而不是：

```text
item.mergeTo
```

### 推荐正式结构

```json
{
  "id": "cook_mushroom_cheese_roll",
  "type": "cook",
  "inputs": [
    {"itemId": "mushroom_x", "count": 1},
    {"itemId": "onion_x", "count": 1},
    {"itemId": "cheese_slice", "count": 1}
  ],
  "toolId": "prep_station",
  "durationSec": null,
  "output": {
    "itemId": "mushroom_cheese_roll",
    "count": 1
  }
}
```

`durationSec` 在研究库里可以为空，但游戏正式配置不能为空。

# 6. Producer 不是“一个生成器对应一条链”

这一点非常重要。

行业实机拆解明确观察到：

- 同一天不同订单要的芝士片、咖啡、茶，其基础元素会来自同一个生成器；
- 肘子、鸡腿的基础元素来自另一个共同生成器；
- 玩家75天记录又显示能量饮料和香槟同来自“饮料柜”。

来源：[S03][S09]

因此 Producer 应是：

```text
Producer
→ Weighted Output Pool
   ├─ Chain A
   ├─ Chain B
   └─ Chain C
```

而不是传统：

```text
Producer
→ 单一 Lv1 Item
```

### 这解释了三个产品现象

**第一，订单可以嵌套。**  
生产一个目标的过程中产生的“副产物”，刚好服务另一个订单。

**第二，棋盘压力被软化。**  
副产物不是纯垃圾，可以很快被别的订单消化。

**第三，真实体力成本高于 2^n。**  
玩家想要 A，但生成器会混合出 A/B/C，导致目标物的期望基础点击数大于理论二合数量。

这也是为什么我们之后必须拿到每个 Producer 的掉落概率，而不能只知道合成级别。

# 10. Day 75 给了我们一个非常好的数值锚点

玩家记录：

```text
能量饮料 + 香槟
均来自饮料柜

估算：
2^9 + 2^7
≈ 700~800 体力
```

来源：[S09]

纯二合理论基础数：

```text
2^9 + 2^7
= 512 + 128
= 640
```

玩家经验是：

```text
700~800
```

所以相对纯理论 640 的实际摩擦倍率约：

```text
700 / 640 = 1.094
800 / 640 = 1.25
```

即：

```text
+9.4% ~ +25%
```

这不是原作官方公式，而是一个非常有价值的 D 级推导。

### 可能贡献摩擦的因素

- 混合掉落；
- 非目标副产物；
- 生成器阶段性冷却；
- 棋盘空间；
- 中间物管理；
- 生产器等级与掉落档位。

因此以后我们的订单成本工具不能只算 `2^level`，必须算概率期望。

# 11. 正确的订单成本模型

## 11.1 单链纯二合

如果某目标完全由基础物合成：

```text
BaseNeed(level) = 2^(level-1)
```

## 11.2 混合生成器

如果基础目标物一次点击出现概率为 `p`：

```text
ExpectedClicks = BaseNeed / p
ExpectedEnergy = ExpectedClicks × EnergyPerTap
```

实际还应加入：

```text
ProducerHigherTierDropBenefit
ProducerCooldown
BoardOverflow
UsefulByproductCredit
```

## 11.3 多输入菜谱

```text
RecipeEnergy
= Σ ExpectedEnergy(input_i)
```

## 11.4 完整订单成本

```text
OrderCost =
  ExpectedEnergy
+ α × CookingWaitSec
+ β × ProducerBlockedSec
+ γ × PeakOccupiedCells
+ δ × ChainContention
- ε × UsefulByproductValue
```

这套模型是我们后续原创产品 Balance Validator 的核心。

# 13. 建设不是独立模拟经营，而是主进度可视化

```text

→ 奖励
→ 修复/扩建
```

- 显示“我做了什么”；
- 给金币提供 Sink；
- 给剧情提供 Trigger；
- 给场景美术提供长期内容载体。

# 17. 卡册系统

玩家社区记录：

```text
一轮 108 张
```

并出现：

- 107/108长期缺最后一张；
- 高星/金色卡；
- 活动卡包大量重复；
- 集齐后立即进入第二轮；
- 有玩家反馈上一轮星星被清零。

来源：[S09]

这些不是我们应该原样复制的“优点”，反而揭示了风险。

### 原创产品建议

必须加入至少一种：

```text
重复卡碎片兑换
保底进度
定向补卡
赛季末缺卡任务
重复保护
```

避免最后1张完全黑箱。

- 体力耗尽时可出现 20 分钟限时能量礼包；
- 具体任务中会出现相应资源补给包；
- 3元、8元被用于低价破冰礼包；
- 限时活动与限时礼包并行。

来源：[S03]

因此商业化不是：

```text
打开商城 → 买东西
```

而是：

```text
目标快完成
+ 时间正在倒数
+ 当前资源刚好耗尽
→ 出现解决当前缺口的礼包
```

这就是它最强、也最容易引发反感的地方。

# 19. 公开评论揭示的摩擦点

2026年9月附近公开玩家反馈集中出现：

- 体力紧；
- 发射器会冷却；
- 活动时间短；
- 烹饪存在明显等待；
- 有玩家称需要约每3小时回来清一次体力；
- 有玩家要求长按发射器自动连续产出；
- 有玩家反馈小程序/App进度不互通；
- 有玩家认为长期活动完成压力偏高。

来源：[S09][S10]

注意：

> 这些属于玩家体验证据，不等于官方固定参数。

尤其广告次数、体力获取、泡泡购买方式等已经出现过版本变化。

# 19.1 跨渠道存档问题已有更明确的公开证据

App Store 2026-06 的玩家评论明确记录：

- 有玩家先在抖音小游戏游玩，下载 App 后即使使用同一手机号/抖音身份也需要重新开始；
- 另有玩家从微信小游戏转 App，发现 App 当时只提供手机号/Apple 等登录方式，无法直接继承微信小游戏进度。

来源：[S01]

这说明“跨渠道统一账号”不是理论上的优化点，而是实际玩家已经遇到的产品摩擦。

原创项目从第一天就应采用：

```text
PlayerId（业务唯一主键）
  └─ AuthBinding[]
      ├─ WeChat
      ├─ Douyin
      ├─ Apple
      ├─ Phone
      └─ Guest
```

渠道身份只能作为绑定，不应直接充当业务存档主键。
