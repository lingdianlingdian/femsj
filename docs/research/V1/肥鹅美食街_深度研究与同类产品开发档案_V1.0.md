# 《肥鹅美食街》深度研究与同类产品开发档案

> 版本：V1.0  
> 研究日期：2026-09-24  
> 用途：竞品拆解、同类产品立项、Cocos Creator / 微信小游戏技术方案、数值与内容生产框架、交付 Codex/AI 开发使用  
> 原则：本档案研究玩法结构与产品方法，不建议复制《肥鹅美食街》的名称、角色、美术、剧情文案、UI皮肤或完整原版数值。

---

## 0. 结论先行

《肥鹅美食街》不是一个“只有二合”的小游戏，而是一个由四个互锁循环组成的产品：

**二合棋盘 → 烹饪加工 → 顾客订单 → 金币建设 → 剧情/新内容解锁 → 回到二合棋盘**

其真正产品价值来自四件事：

1. **把普通 Merge-2 改造成“食材 + 厨具 + 时间加工”的烹饪系统**，让中间过程不再只是无脑一路二合。
2. **用“经营天数”而不是传统玩家等级承载主线**，玩家会直观理解“今天要做完一组菜单”。
3. **把主线、建设、剧情、活动、卡册全部挂在同一个订单/体力消耗系统上**，因此新增活动的研发成本低，但可持续创造消耗与付费需求。
4. **商业化核心不是直接卖菜，而是卖“差一点就能完成”的时间与体力**：体力、生产器冷却、烹饪时间、活动倒计时同时形成约束。

从开发角度看，这类游戏的核心难度并不在程序，而在：

- 合成链/发射器/菜谱的数据设计；
- 每日订单节奏；
- 体力与冷却的曲线；
- 棋盘空间压力；
- 建设与剧情内容量；
- 活动框架的可配置化。

因此，若目标是做一款“同类型但原创”的微信小游戏，推荐采用 **Cocos Creator 3.8 LTS + TypeScript + 配置驱动 + 轻量后端 + 远程活动配置**。程序本体可高度复用，真正需要持续生产的是配置、美术、剧情和活动。

# 4. 新手前 10 分钟流程

公开实机拆解显示，新手阶段不是直接把完整棋盘扔给用户。

## 4.1 教学棋盘

- 先使用 **4×7** 的小棋盘教学；
- 教学内容至少包含：
  - 点击发射器；
  - 产出食材；
  - 两两合成；
  - 解锁棋盘块；
  - 交付订单。

之后才进入完整主棋盘。

## 4.2 主棋盘

公开实机拆解明确给出完整棋盘为 **9×7 = 63 格**。

这是一项很重要的产品选择：

- 63 格足够制造空间管理压力；
- 但手机竖屏仍可保证单格足够大；
- 可通过“锁区”制造阶段解锁目标；
- 不需要无限扩盘。

## 4.3 锁区设计

未解锁区域不是单格散锁，而更像“整块区域锁定”，且会标注：

- 需要到达的经营进度；
- 解锁奖励。

优点：

1. 玩家知道“为什么还不能用”；
2. 玩家有明确短期目标；
3. 设计者可提前预埋高级生成器或奖励；
4. 比随机散落的灰格更容易做视觉组织。

# 5. 二合棋盘系统

## 5.1 基础规则

典型操作：

1. 点击可生产的发射器；
2. 消耗 1 点体力；
3. 生成一个物品到空格；
4. 两个相同等级物品拖拽合并；
5. 获得下一等级物品；
6. 高等级物品用于直接交付，或进入厨具加工；
7. 交订单后清除物品并结算奖励。

## 5.2 物品类型建议拆分

开发时不要把所有东西都写成 `Item` 然后堆 if/else，应至少分为：

| 类型 | 功能 |
|---|---|
| Ingredient | 普通食材链 |
| Producer | 发射器 |
| Cookware | 厨具/加工器 |
| Dish | 已完成菜品 |
| RewardItem | 体力球、金币、钻石等 |
| Container | 箱子/礼包/卡包 |
| Special | 活动道具、解锁物 |
| Blocker | 锁定、灰尘、纸箱等障碍 |
| Bubble/Temp | 临时奖励或限时物品 |

## 5.3 合成

基础：

```text
Item(Lv n) + Item(Lv n) → Item(Lv n+1)
```

如果一条合成链完全由 Lv1 生成，则理论最小基础产出数：

```text
NeedBase(Lv n) = 2^(n-1)
```

示例：

- Lv1 = 1
- Lv2 = 2
- Lv3 = 4
- Lv4 = 8
- Lv5 = 16
- Lv8 = 128
- Lv10 = 512

因此 Merge-2 的难度增长天然是指数型的，这也是后期非常容易出现“一个订单几百体力”的根本原因。

# 6. 发射器 Producer 系统

## 6.1 已确认行为

实机与公开资料明确存在：

- 发射器带闪电标记；
- 点击消耗体力；
- 产生基础或中低级食材；
- 连续点击一定次数后进入冷却；
- 高等级发射器会提升生产效率；
- 部分特殊活动可以临时提供“无限量相关发射器”。

## 6.2 推荐数据结构

```json
{
  "producerId": "vegetable_crate_lv3",
  "energyCost": 1,
  "capacity": 12,
  "cooldownSec": 1800,
  "outputPool": [
    {"itemId": "veg_lv1", "weight": 70},
    {"itemId": "veg_lv2", "weight": 25},
    {"itemId": "veg_lv3", "weight": 5}
  ],
  "upgradeTo": "vegetable_crate_lv4"
}
```

## 6.3 发射器状态机

```text
LOCKED
  ↓ unlock
READY
  ↓ tap
PRODUCING
  ↓ capacity exhausted
COOLDOWN
  ↓ time complete
READY
```

特殊状态：

```text
BOOSTED
UNLIMITED_EVENT
DISABLED
```

## 6.4 为什么升级发射器重要

Apple 编辑推荐的官方产品介绍明确建议“优先升级发射器”，因为高级发射器提升食材产出效率。

从数值设计上，升级应至少影响：

- 高等级掉落概率；
- 单轮容量；
- 冷却时间；
- 稀有分支概率。

不要只增加“每次多掉一个”，否则棋盘会瞬间爆仓。

# 7. 厨具与烹饪系统——本作最值得研究的差异点

普通 Merge 游戏通常是：

```text
合成 → 交付
```

《肥鹅美食街》加入：

```text
合成食材 → 将食材放入对应厨具 → 等待 → 成品菜 → 交付
```

这相当于在 Merge 之后加入一个“小型制造系统”。

## 7.1 烹饪配方

示例来自早期经营菜单：

- 生菜 → 生菜沙拉
- 蓝莓 → 鲜榨蓝莓汁
- 柠檬 → 手打柠檬汁
- 蘑菇 + 芝士相关食材 → 菌香芝士卷
- 爆米花、苹果果饮、珍珠奶茶等成品

## 7.2 推荐 Recipe Schema

```json
{
  "recipeId": "salad_001",
  "cookwareId": "mixing_bowl",
  "inputs": [
    {"itemId": "lettuce_lvX", "count": 1}
  ],
  "output": "lettuce_salad",
  "cookTimeSec": 120,
  "unlockDay": 5,
  "speedupGemPerMin": 1
}
```

## 7.3 Cookware 状态机

```text
IDLE
  ↓ input valid
COOKING
  ├─→ SPEED_UP
  └─→ time end
READY_TO_COLLECT
  ↓ collect
IDLE
```

## 7.4 烹饪层的产品意义

它同时增加了四种压力：

1. **体力压力**：先做食材；
2. **空间压力**：中间材料必须留在盘上；
3. **时间压力**：菜还要做；
4. **排产压力**：同一个厨具被多个订单抢占。

这比单纯把合成链从 8 级拉到 10 级更有游戏性。

# 8. 订单系统

## 8.1 表现形式

棋盘上方会持续显示顾客订单卡：

- 顾客头像；
- 需要的 1~N 个物品；
- 当前拥有数量；
- 金币奖励；
- 可能附带活动进度/额外奖励。

公开截图可见屏幕同时展示多个订单，实际开发建议维持 **2~4 个并行订单槽**。

## 8.2 订单类型

### A. 单品订单
```text
番茄 ×1
```

### B. 多材料订单
```text
洋葱 ×1 + 咖啡 ×1
```

### C. 成品菜订单
```text
菌香芝士卷 ×1
```

### D. 混合订单
```text
成品菜 + 原料 + 饮品
```

## 8.3 “经营菜单”

玩家社区已系统记录每天订单，说明至少较大部分主线订单是可预测或固定配置，而不是纯随机。

截至公开攻略：

- 第 1~10 天有明确菜单记录；
- 80+ 天存在完整攻略；
- 101~105 天存在菜单；
- 106~110 天也已有玩家提及。

因此，推荐同类产品主线也采用 **固定章节配置 + 可控随机辅助订单**，而不是完全 RNG。

# 10. 主线“经营天数”系统

玩家反馈明确说明：游戏“根据完成订单天数来算等级”。

因此可把一个经营天理解为：

```text
Day
├─ Order 1
├─ Order 2
├─ Order 3
├─ ...
├─ Day Reward
├─ Build Progress
└─ Story Trigger
```

## 推荐状态机

```text
DAY_LOCKED
  ↓ previous day cleared
DAY_ACTIVE
  ↓ orders completed
DAY_SETTLEMENT
  ↓ collect
BUILD_OR_STORY
  ↓ done
NEXT_DAY
```

## 为什么比传统 Level 好

“第 35 天”比“Lv.35”更适合经营游戏，因为玩家会天然理解：

- 今天开张；
- 今天菜单；
- 今天收入；
- 今天装修；
- 明天有新顾客。

“天”本身就是叙事容器。

# 11. 美食街建设系统

## 11.1 已确认结构

公开资料显示：

- 完成订单获取金币；
- 金币投入美食街建设；
- 从破败场景逐步恢复；
- 解锁店铺；
- 后续扩展街道路面、桌椅、灯光、喷泉等；
- 建设进度与主线进度、剧情解锁挂钩；
- 店铺建成后，美食街顾客数量与场景活力逐渐增加。

## 11.2 这是“可视化进度条”

建设玩法本身并不需要复杂经营模拟。

其主要作用：

1. 把抽象的订单进度转成场景变化；
2. 提供金币消耗口；
3. 触发剧情；
4. 让玩家感觉自己拥有一条街；
5. 为长期美术内容提供承载空间。

# 14. 体力系统

## 14.1 当前公开体验特征

玩家评论多次出现一致信息：

- 自然恢复约 **2 分钟 / 1 点体力**；
- 自然恢复上限 **100**；
- 后期高阶订单可能需要 100+，甚至数百体力；
- 当前版本玩家反馈存在每日有限次数广告换体力；
- 一条 2026 年玩家反馈明确写到约 **4 次广告 × 15 体力**；
- 有玩家反馈钻石购买 100 体力的价格会逐次提高，例如第一次 10 钻、之后 20 钻；
- 主线推进、建设等节点会返还少量体力；
- 第一次耗尽体力时存在新手期友好恢复/引导。

> 注意：广告次数和钻石档位会被运营配置修改，因此不应把社区数字当成永久固定值。

## 14.2 体力设计公式

建议开发时定义：

```text
NaturalEnergyPerDay
= min(24h / RegenInterval, 实际上线可领取量)
```

如果：

```text
RegenInterval = 120 sec
Cap = 100
```

则从 0 回满：

```text
100 × 2min = 200min = 3h20min
```

这天然推动玩家一天多次上线。

# 15. 后期难度证据

一位社区玩家对第 75 天某订单的估算提到：

- 同时需要两条高阶饮料；
- 其合成基础消耗可接近 **700~800 体力**。

另有多个玩家在 25 天、35 天、90 天阶段反馈：

- 单订单体力显著增加；
- 35 天以后卡关 1~2 天并不少见；
- 免费体力一天可能只能完成少量订单。

这说明原作长线不是通过“复杂操作”提高难度，而主要通过：

```text
高阶合成指数成本
+ 生产器容量
+ 生产器冷却
+ 烹饪时间
+ 棋盘空间
+ 限时活动竞争
```

来控制速度。

# 16. 钻石系统

钻石承担至少四类用途：

1. 购买体力；
2. 商店购买指定物品；
3. 跳过/缩短烹饪或冷却；
4. 活动/礼包/特殊资源。

公开商店截图可见：

- 单个特定材料可直接以钻石购买；
- 每类商品带购买次数限制；
- 商店存在刷新倒计时；
- 可以付费钻石刷新。

这使钻石不只是“体力货币”，还是“绕过 RNG 和时间”的通用硬通货。

# 19. 活动框架开发方式

不要每个活动写一套代码。

应建立统一 Event Framework：

```text
EventDefinition
├─ StartAt
├─ EndAt
├─ UnlockCondition
├─ ProgressSource[]
├─ Milestone[]
├─ RankingRule?
├─ RewardTable
├─ EventShop?
├─ EventBoard?
├─ OfferGroup
└─ SettlementRule
```

ProgressSource 建议统一为事件总线：

```text
MERGE_ITEM
PRODUCE_ITEM
COOK_START
COOK_COMPLETE
ORDER_COMPLETE
DAY_COMPLETE
COIN_SPEND
ENERGY_SPEND
BUILD_COMPLETE
```

这样“芝士漂流”可以完全通过配置完成。

# 20. 卡册系统

卡册是很强的长期 Meta，因为它：

- 不占主棋盘格子；
- 可以作为任何活动的终极奖励；
- 可以加入稀有度；
- 可以制造重复；
- 可以赛季重置；
- 很容易做付费补缺。

推荐结构：

```text
AlbumSeason
├─ Set A
│  ├─ Card 1 ★
│  ├─ Card 2 ★★
│  └─ ...
├─ Set B
└─ Completion Rewards
```

不要让“最后一张卡”完全黑箱。

建议增加：

- 重复卡兑换；
- 保底进度；
- 定向选卡；
- 赛季末补卡任务。

这能明显降低原作玩家社区对卡包重复的负反馈。

# 21. 玩家主要痛点——竞品最值得改进的地方

2026 年 App Store 与 TapTap 评论呈现非常一致的负面集中点。

## 21.1 体力恢复慢
- 2 分钟 1 点；
- 上限 100；
- 后期高阶订单几百体力；
- 很容易上线几分钟后再次离开。

## 21.2 发射器冷却叠加
即使有体力，也可能因为产出器进入冷却而卡住。

## 21.3 烹饪等待
部分菜品制作时间可长达几十分钟。

## 21.4 活动时间短
活动目标与主线共用体力，玩家会同时争夺同一资源。

## 21.5 频繁付费弹窗
“差一点”节点与礼包高度绑定，部分玩家明显产生反感。

## 21.6 不能长按连续产出
社区玩家明确提出，一直单击发射器操作疲劳。

## 21.7 跨渠道进度不互通
玩家反馈：

- 微信小程序与 App 进度不能直接同步；
- 同手机/账号也可能需要重开。

对于新产品必须从架构第一天解决。

## 21.8 活动结束未领取奖励处理
玩家反馈活动结束后未领取资源可能不自动入账。

新产品应默认自动结算到邮箱/待领取仓库。

# 22. 我们做同类产品时应采用的改良方案

## 改良 1：体力不是唯一瓶颈

原作后期体力约束过强。

建议：

- 主线主要受体力影响；
- 厨具等待主要受时间影响；
- 活动给独立少量活动体力，避免全部抢主线体力。

## 改良 2：高阶订单难度限制

定义订单总成本：

```text
OrderCost
= ExpectedEnergy
+ TimeWeight × CookMinutes
+ SpaceWeight × PeakOccupiedCells
+ CooldownWeight × ProducerWait
```

不能只按“物品等级”出单。

建议正常订单：

- 前期：10~35 等效体力；
- 中期：40~100；
- 后期常规：80~180；
- 200+ 应作为明确的“大单/高奖励单”；
- 500+ 不应成为大量日常订单。

## 改良 3：长按生产

```text
LongPress Producer
→ 每 100~150ms 自动尝试生产
→ 体力不足/满盘/容量空时停止
```

## 改良 4：菜谱排产队列

厨具可显示：

- 当前菜；
- 剩余时间；
- 下一槽；
- 一键领取。

避免玩家必须频繁点开。

## 改良 5：活动保底

进度活动最后 10% 不应该完全只能氪金。

可以：
